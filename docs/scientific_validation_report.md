# Scientific Validation Report — ICS Bayesian Risk Assessment Framework

**Date:** August 2026
**Scope:** Deep scientific, mathematical, methodological, functional and professional
audit of the entire platform (backend, frontend, database, topology ingestion,
probabilistic model, risk model, outputs, tests, documentation).
**Method:** Full-code inspection + reconstruction of the mathematical pipeline +
independent mathematical verification (brute-force enumeration, closed-form
recomputation) + end-to-end execution of the real platform (CLI, API, PDF
exports, sensitivity analysis) + the complete existing test suite.

---

## 1. Executive summary

The platform implements a **coherent and largely defensible quantitative ICS
risk-assessment methodology**. The core scientific claims are backed by real
implementations, not decoration:

- CVSS v3.1 scores are computed with the **official FIRST equations**
  (`backend/cvss.py`), verified against published scores.
- CVSS is correctly treated as a **severity score, not a probability**; the
  severity→probability mapping is an **explicit, configurable logistic model**,
  honestly labelled as a modelling assumption.
- Bayesian inference is **genuine**: pgmpy Variable Elimination over CPTs
  generated by a correct **Noisy-OR** parameterisation. Posterior probabilities
  were re-derived by an independent brute-force joint enumeration and match to
  machine precision.
- The risk metric is a **transparently defined, bounded ranking index**
  (P × normalised impact), never presented as a probability or expected loss.
- The pipeline is **deterministic** (bit-identical outputs for identical
  inputs and settings), and **settings are now recorded in every output**,
  making results traceable and reproducible.

**Overall classification: the platform is suitable for professional use as a
risk-ranking decision-support tool, provided (a) the explicit modelling
assumptions are respected, (b) parameters are calibrated against organisational
data before operational use, and (c) outputs are interpreted as modelled
probabilities without a time horizon, not as calibrated frequencies.**

Two HIGH-severity defects were found and fixed during this audit (see §14):
the documented `scope` blast-radius multiplier was silently dropped by the
topology normalizer (dead feature), and no output recorded the settings
snapshot used (traceability/reproducibility gap — the local database contained
stale non-default settings that silently changed every result).

## 2. Architecture audit

**Pipeline (reconstructed from code):**

```
Topology (JSON/YAML/CSV/XLSX/GraphML/XML/AML/VSDX/VDX)
   ↓  importers → normalize_asset / normalize_relationship (topology.py)
   ↓  validate_graph: unknown assets/types rejected, self-loops & dup edges removed,
   ↓                   cycles rejected (DAG required), disconnected subgraphs warned
   ↓  enrich_graph (enrichment.py): kind/zone/vendor inference, attribute defaults
   ↓  build_graph_skeleton (graph_builder.py): pgmpy DAG + edge weights
   ↓  compute_base_probs (probability.py): intrinsic probabilities (logistic + log-odds)
   ↓  parameterize (cpt_generator.py): Noisy-OR CPTs, model.check_model()
   ↓  check_evidence_feasibility → ImpossibleEvidenceError on zero-probability evidence
   ↓  compute_posteriors_with_evidence (inference.py): pgmpy Variable Elimination
   ↓  build_risk_table (risk.py): Risk Index = P × (severity/10) × scope_mult × weight
   ↓  compute_aggregate_risk: max/mean/median + level counts
   ↓  compute_attack_paths (attack_paths.py): directed DAG paths, weakest-link × target risk
   ↓  outputs.py / pdf_reports.py / database persistence / REST API / React UI
```

**Observations:**

- The layered architecture (ingestion → normalization → validation → enrichment →
  BN construction → inference → risk → reporting) is clean and each stage has a
  well-defined responsibility. No dead or misleading stages were found.
- Input validation is strict and actionable (out-of-range attributes rejected,
  not silently clamped; `.vsd` rejected with conversion guidance instead of an
  unverifiable claim).
- The REST API is stateless, rate-limited, auth-optional, with structured
  errors and request-ID tracing — appropriate for professional use.
- The settings store is **persistent (SQLite)** and process-global; this is the
  root of the traceability issue fixed in this audit (§14).

## 3. Mathematical audit

| Component | Formula implemented | Independent check | Verdict |
| --------- | ------------------- | ----------------- | ------- |
| CVSS v3.1 Base Score | Official FIRST equations incl. Roundup and scope-changed 1.08 factor | Official published scores (Heartbleed 7.5, Log4Shell 10.0, Shellshock 9.8) | **Correct** |
| CVSS→probability | `1/(1+exp(−k(CVSS−x₀)))`, k=0.8, x₀=5.0 default | Independent sigmoid evaluation across the range, incl. anchor points (CVSS 5→0.5, 10→≈0.98, 0→≈0.018) | **Correct** (model assumption, see §4) |
| Log-odds context adjustment | `logit(P)=logit(P₀)+Σw·ln(M)` | Independent recomputation of log-odds arithmetic | **Correct** |
| Noisy-OR CPT | `P=1−(1−leak)·Π(1−qᵢ)` | Closed-form row-by-row recomputation for multi-parent nodes; normalisation P(0)+P(1)=1 for every parent configuration; monotonicity | **Correct** |
| Bayesian inference | Exact Variable Elimination (pgmpy) | Brute-force enumeration of the full joint for chain (X→Y→Z) and collider (A→X←B) structures, with and without evidence | **Correct** (matches to 1e-9) |
| Risk Index | `P × (severity/10) × scope_mult × impact_weight` | Independent recomputation from definition | **Correct** |
| Scope multiplier | `1+(scope−1)×0.1`, scope∈[1,5] | Independent evaluation; **regression: attribute now survives normalization** | **Correct after fix** |

**Numerical validity:** all base and posterior probabilities verified in [0,1];
all CPT rows normalise to 1; no NaN/Inf/negative probabilities observed across
the full test suite; a `math.exp` overflow path in the sigmoid for extreme-but-
valid settings was eliminated (numerically stable branch).

**Units/scales:** probabilities are 0–1; CVSS is 0–10; consequence severity is
0–10; Risk Index is 0–≈1.4. The UI displays probabilities as 0–1 decimals
(never as a misleading percentage), severity as 0–10, and Risk Index as a
decimal — verified in `frontend/src/utils.ts` and all chart components.

## 4. Probability-model audit

Every probability produced by the platform was audited against the questions
*what event, what definition, what inputs, what assumptions, prior or
posterior, conditional, what time horizon, calibrated?*

| Probability | Event | Prior/Posterior | Conditional | Time horizon | Calibrated? |
| ----------- | ----- | --------------- | ----------- | ------------ | ----------- |
| Intrinsic probability | "Asset compromised due to its own attributes within the assessment scenario" | Prior (Noisy-OR leak) | Unconditional | **Undefined** | **No** (expert-configured logistic + multipliers) |
| Posterior probability | "Asset compromised given evidence and the modelled network" | Posterior | Conditional on evidence | **Undefined** | **No** |
| CPT entries | "Child compromised given parent states" | Conditional (modelled) | Conditional on parents | Undefined | **No** |
| Attack-path score | Not a probability (weakest-link heuristic × risk) | — | — | — | n/a |

**Key conclusions:**

1. All probabilities are **modelled (model-conditional) probabilities** for the
   assessment scenario. They are **not** empirically calibrated and have **no
   time horizon** (not per-day/month/year). The report and README now state
   this explicitly. This is the single most important honesty requirement and
   it is satisfied.
2. The CVSS→probability curve is a **documented, configurable modelling
   assumption** (logistic, k/x₀), *not* a disguised empirical calibration.
   `P = CVSS/10` is only available as an explicitly deprecated legacy mapping.
3. No probability is ever exactly 0 or 1 except by explicit analyst override
   (`p_base_override: 0`) — preserving updatability and enabling the
   `IMPOSSIBLE_EVIDENCE` diagnostic.
4. The human-factor model (role-based phishing base rate × (1−awareness) ×
   privilege) is an expert-elicited engineering model; the guest-rate of 0.5
   and role base rates are plausible but uncalibrated. This is disclosed.

**Classification:** intrinsic and posterior probabilities are **B (defensible
engineering model)** — mathematically sound, honestly documented, but not
empirically calibrated.

## 5. Bayesian Network audit

- **Structure:** a DAG over asset nodes; edges follow the validated topology
  relationships. Cycles are rejected at ingestion (`validate_graph`), so the
  BN is guaranteed acyclic.
- **Node semantics:** binary nodes `0`=safe, `1`=compromised; asset kinds
  (device/human/physical) have distinct, documented base-probability models.
- **Edge semantics:** directed causal edges parent→child; direction follows the
  relationship as supplied by the analyst. The framework documents that
  reversing direction would invert causal semantics (fixed in a prior audit).
- **CPT semantics:** Noisy-OR with leak = intrinsic probability. This is a
  defensible, interpretable parameterisation for binary causes under the
  independence-of-causal-influence assumption (Pearl, 1988). It is explicitly
  disclosed as a modelling choice, and the leak conflation (residual common
  cause vs intrinsic vulnerability) is documented in `model-assumptions.md`.
- **Conditional independence:** the Markov property is assumed per the graph
  structure; the report discloses that correlated vulnerabilities / shared
  infrastructure are not explicitly modelled (§13).

**Verdict: the network is a genuine BN — inference is exact and the
probabilistic semantics are coherent.** Classifications: structure **B**
(edges are analyst-supplied causal assumptions), inference **A** (exact).

## 6. Risk-model audit

- **Definition:** `Risk Index = P(compromised|evidence) × Impact`, with
  `Impact = (severity/10) × scope_multiplier × impact_weight`.
- **Interpretation:** a bounded ranking index in [0, ≈1.4]; **not** a
  probability, **not** expected loss, **not** ALE. The UI, PDF, and CLI
  consistently describe it as an index, and Probability/Impact/Risk are shown
  as separate columns so the product is transparent.
- **Aggregation:** network risk = worst-case single-asset index (max), plus
  mean/median and per-level counts. Severity-weighted means (which double-count
  severity) were removed in a prior audit.
- **Thresholds:** Low/Moderate/High/Critical are defined by a single
  configurable threshold set (defaults 0.25/0.50/0.75), consumed uniformly by
  the API, PDF, CLI, and UI. The thresholds are **honestly labelled as
  engineering calibration placeholders**, not derived from a formal standard.
- **Criticality vs probability:** consequence severity is an impact input only;
  it never enters the probability computation. No conflation.

**Verdict: B (defensible engineering model).** The risk index has a clear,
traceable definition and bounded range; its interpretation as a ranking index
is consistently communicated.

## 7. CVSS audit

- **Version:** v3.1 only; v4.0 vectors rejected with guidance.
- **Computation:** official FIRST equations in `backend/cvss.py` (no
  proprietary formula); verified against published scores.
- **Source:** analyst-supplied vulnerability records (CVE + vector + score).
  The framework does **not** fetch from NVD at runtime — `source` is
  descriptive provenance metadata, and this is documented honestly.
- **Aggregation:** effective score = **max** over vulnerabilities (worst-case
  severity), a documented modelling decision. Vulnerability *count* is not
  modelled (§13).
- **CVSS→probability:** logistic calibration model with configurable k/x₀,
  documented as a modelling assumption, never presented as
  "CVSS 8.0 = 80% probability". The platform explicitly warns against this.

**Verdict: A (implementation) / B (severity→probability mapping, honestly
labelled as an assumption).**

## 8. Evidence / inference audit

- **Evidence semantics:** hard binary evidence `{asset: 0|1}` (Compromised/Safe);
  "Unknown" = no evidence. Uncertain/soft evidence is not modelled — disclosed.
- **Validation:** unknown nodes and non-binary states are rejected
  (`EvidenceError`); contradictory duplicate evidence rejected at the API layer.
- **Impossible evidence:** zero-probability evidence (e.g. a node with
  `p_base_override: 0` asserted Compromised) is detected **before** inference
  and returned as a structured `IMPOSSIBLE_EVIDENCE` diagnostic with affected
  nodes — never silently presented as an all-zero result. This distinction
  (Prior → Evidence → Posterior) is reflected in the UI.
- **Inference:** exact Variable Elimination; verified against brute-force joint
  enumeration. Evidence nodes are pinned exactly to their asserted state; the
  UI marks them "Pinned by evidence".

**Verdict: A (correctness), B (certainty assumption disclosed).**

## 10. Reproducibility audit

- **Determinism:** the model pipeline is fully deterministic (no randomness;
  the graph image uses a fixed `seed=7`). Running the same assessment twice
  yields bit-identical posteriors, risk tables, and rankings (verified by
  `test_assessment_is_deterministic`).
- **Settings persistence (fixed):** analysis outputs previously recorded **no**
  settings snapshot, so "same inputs, different results" could occur silently
  when the persisted settings store changed. This audit adds `settings_used`
  (full model-parameter snapshot) to the result dict, `metrics.json`,
  `summary.txt`, the PDF "Model Parameters" section, and the REST API, plus a
  visible warning whenever active settings differ from framework defaults.
  Any reviewer can now trace a number back to the exact parameters.
- **Remaining caveat:** settings are process-global and shared; concurrent
  requests changing settings mid-flight are possible (documented in
  `temporary_settings`). Single-user/serial usage is unaffected.

**Verdict: B → A after the settings-traceability fix.**

## 11. ICS realism audit

The model reflects meaningful ICS characteristics rather than treating the
plant as a generic IT network:

- Asset kinds distinguish **devices** (PLC/RTU/HMI/SCADA/historian…), **humans**
  (operators/engineers/admins with role-based phishing susceptibility), and
  **physical processes** (expert `p_base_override`), each with a different
  probability model.
- Relationship types (`controls`, `actuates`, `monitors`, `connects-to`,
  `programs / operates`) carry distinct causal weights — causal semantics, not
  bare connectivity.
- Firewalls, industrial protocols (Modbus, DNP3, OPC-UA, Profinet, S7comm…),
  Purdue/zone trust levels, and MITRE ATT&CK for ICS techniques modulate
  propagation.
- Consequence severity places safety/availability at the top of the impact
  scale, matching ICS risk priorities.

**Disclosed simplifications:** connectivity implies causal propagation with a
configured weight (reachability/trust/exploitability are collapsed into one
weight); defence-in-depth interactions beyond a static firewall factor are not
modelled; a single asset attribute drives each probability. These are stated
explicitly in `model-assumptions.md` and are defensible for a first-order
screening tool.

**Verdict: B — credible ICS-aware modelling with explicit simplifications.**

## 13. Limitations (explicit, unchanged by this audit)

1. **No empirical calibration.** Every parameter (k, x₀, multipliers, weights,
   thresholds) is an expert judgment or framework default. Organisations must
   calibrate against their own incident data.
2. **No time horizon.** Probabilities are model-conditional for the assessment
   scenario; they are not frequency estimates per day/month/year.
3. **Analyst-supplied vulnerability data.** No live NVD/CVE retrieval.
4. **Binary node states only;** no continuous or multi-state variables, no time
   dynamics.
5. **Certain evidence only** (no uncertain/soft evidence).
6. **Vulnerability count not modelled** — only worst-case severity drives the
   intrinsic probability; multiple independent vulnerabilities on one asset do
   not increase it further.
7. **Noise-OR independence assumption** (conditional independence of causes
   given the child) and **Markov conditional independence** are assumed;
   correlated vulnerabilities, shared infrastructure and common-cause failures
   are not explicitly modelled.
8. **Leak = intrinsic probability**: residual common-cause risk is not
   separately parameterised (documented in `model-assumptions.md`).
9. **Risk Index is a ranking index**, not expected loss or monetary exposure.
10. **Edge weights collapse reachability/trust/exploitability** into a single
    configured number; defence-in-depth beyond a static firewall factor is not
    modelled.
11. Exact Variable Elimination scales with network treewidth; measured guidance
    exists in `tests/test_performance.py`.

## 15. Remaining risks (post-correction)

- **Uncalibrated parameters** remain the dominant scientific limitation. The
  sensitivity-analysis module quantifies how much outputs move under
  one-at-a-time perturbations, but no statistical uncertainty model exists.
- **Stale non-default settings** currently exist in the local SQLite store
  (from a previous session). They are now *visible* in every output and can be
  reset via Settings → Reset or `POST /settings/reset`; organisations should
  review them.
- **Attack-path scores are heuristic** (weakest-link × target risk) and are
  labelled as such.
- **Structural-zero evidence edge case** documented in `model-assumptions.md`
  §12 (a child with leak 0 and parent weight 1 evidenced in contradiction)
  surfaces as near-zero rather than exactly-zero — not pre-checked; acceptable,
  disclosed.
- Exact inference performance on very large/high-treewidth topologies.

## 16. Recommended future improvements (not required for validity)

1. **Calibration pipeline**: fit k/x₀ and multipliers to organisational
   incident/telemetry data; expose a calibration report.
2. **Time-horizon parameter**: add an explicit annualised or assessment-period
   interpretation, or keep the "model probability, no horizon" language (current
   approach is defensible).
3. **Uncertain evidence**: support soft/uncertain evidence (likelihood ratios)
   in the inference layer.
4. **Vulnerability-count effect**: model multiple independent vulnerabilities
   per asset (e.g. via a second Noisy-OR layer) rather than worst-case severity
   only.
5. **Uncertainty quantification**: posterior sensitivity or simulation-based
   bounds, clearly labelled (do not fabricate confidence intervals without a
   statistical model).
6. **Correlation structure**: model shared infrastructure/zone correlation
   explicitly (common-cause nodes) where justified.
7. **Scenario templates**: packaged attack scenarios (ransomware, remote
   access, supply chain) as reusable evidence+settings bundles.
8. **NVD integration** as an optional enrichment source (with explicit
   provenance tagging), if licensing/operational constraints permit.

recorded `settings_used` snapshot, (c) an explicit list of assumptions

validity than has been demonstrated.
