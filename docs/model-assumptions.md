# Model Assumptions — ICS Bayesian Risk Framework

This document is the authoritative statement of the modelling assumptions
behind every number the framework produces. It exists so that an ICS
cybersecurity professional, a Bayesian-modelling reviewer, or an internship
evaluator can inspect the system and distinguish clearly between:

- what is **mathematically established** (e.g. probability axioms, CVSS v3.1
  scoring equations, exact variable elimination),
- what is **modelled** through explicit assumptions,
- what is **configurable** by the analyst, and
- what remains an **assumption** (i.e. not empirically calibrated).

> Reading guide: every section ends with an explicit statement of which parts
> are exact, which are modelled, and which are calibrated (or not).

---

## 1. CVSS assumptions

- CVSS v3.1 Base Score is computed with the **official FIRST equations**
  (`backend/cvss.py`), from a parsed CVSS vector. This part is exact and
  deterministic.
- A CVSS Base Score is a **severity metric** in `[0, 10]`. It is **not** a
  probability of compromise.
- The framework therefore never treats `P = CVSS / 10` as its primary model.
  The legacy linear mapping exists only for backward compatibility and is
  explicitly labelled "not recommended" in the UI and settings.
- Default mapping: `logistic`, with `P₀ = 1 / (1 + exp(−k·(CVSS − x₀)))`,
  `k = 0.8`, `x₀ = 5.0`. **These k/x₀ values are expert defaults; they are
  not empirically calibrated** and should be calibrated by an organisation
  against its own incident data.

## 2. Vulnerability-data assumptions

- Vulnerability records are **analyst-supplied**. The framework does **not**
  retrieve data from NVD or any external service at runtime.
- A record such as `{"cve_id": "CVE-2017-0144", "vector": "...", "source": "NVD"}`
  means *this vector was originally published by NVD and entered by an
  analyst*; it does **not** mean the framework queried NVD.
- CVE identifiers are validated syntactically (`CVE-\d{4}-\d{4,}`) and CVSS
  vectors are parsed and validated before scoring.
- The "effective" CVSS of an asset is the **maximum** over its listed
  vulnerabilities. Taking the maximum is a modelling decision: it reflects
  worst-case severity, not likelihood.
- **Not calibrated**: no inference is made about which vulnerability is more
  likely to be exploited; only severity is ranked.

## 3. Intrinsic-probability assumptions

The intrinsic compromise probability of an asset is:

```
base     = logistic(CVSS)  or legacy linear(CVSS)   # configured mapping
lo       = ln(base / (1 − base))                    # log-odds space
lo      += Σ w_i · ln(m_i)                          # contextual multipliers
p_int    = 1 / (1 + exp(−lo)), capped to [1e-6, 0.9995]
```

Contextual multipliers include exposure, patch, protocol, trust, and MITRE
ATT&CK technique effects, plus configurable exposure/patch weights.

- Combining multipliers **additively in log-odds space** assumes the effects
  are multiplicatively independent in odds space. This is a standard, explicit
  modelling assumption; it is not empirically validated for ICS.
- The soft cap `P_BASE_CAP = 0.9995` ensures the model never returns exact
  probabilities of 0 or 1, so downstream evidence never becomes trivially
  impossible from floating-point collapse. Exact 0/1 can still occur via
  `p_base_override`.
- **Calibration status: not empirically calibrated.** All multiplier values
  are expert/framework defaults (see `docs/parameter-provenance.md`).

## 4. Propagation assumptions

- A directed edge carries a **Noisy-OR causal weight** `w ∈ [0,1]`, **not**
  the literal conditional probability `P(target=1 | source=1)`.
- The implied single-active-parent conditional probability is:
  `P(target=1 | parent=1) = 1 − (1 − leak) × (1 − w)`, where `leak` is the
  target's intrinsic probability.
- Assumption: a child becomes compromised with the given probability if at
  least one parent is compromised; multiple active parents combine through the
  Noisy-OR rule `P = 1 − (1 − leak) × Π(1 − wᵢ)`. This assumes the parents
  are conditionally independent *given the child's state* (the canonical
  Noisy-OR assumption).
- A firewall multiplies the *propagated* probability by a configured factor
  (default 0.30, i.e. ~70% reduction, consistent with NIST SP 800-41
  guidance that a properly configured firewall blocks roughly 70% of
  network-borne attacks). This is a **literature-consistent default**, not
  measured data from the organisation.

## 5. Noisy-OR CPT assumptions

- Every non-root node's CPT row is generated by the closed form
  `P(node=1 | S) = 1 − (1 − leak) × Π_{i ∈ S} (1 − wᵢ)`, with `leak`
  equal to the node's intrinsic probability.
- The leak parameter conflates "all other causes not modelled explicitly"
  with "this asset's own intrinsic vulnerability". This is an explicit
  simplification: in the current model the leak is **not** a separate
  tunable quantity; it equals the intrinsic probability. Model designers
  should be aware that distinguishing residual common-cause risk from
  intrinsic vulnerability would require a richer parameterisation.
- Noisy-OR CPTs keep the network small and exact inference tractable; they
  are a modelling choice, not a physical law.

## 6. Bayesian Network assumptions

- The network is a DAG: asset nodes are binary (`0` = safe, `1` =
  compromised), edges follow the validated topology relationships.
- Inference uses **exact Variable Elimination** (pgmpy), which is
  mathematically exact for the given model.
- Assumptions carried into the network: conditional independence per the
  graph structure (Markov property), and binary node states. No continuous
  variables, no time dynamics, no defence-in-depth layering beyond the
  configured edge weights.
- Scalability: exact inference is exponential in the network's treewidth.
  Practical limits depend on topology; see `tests/test_performance.py` for
  measured timings on 10/25/50/100-node chains, and the README's limitations
  section.

## 7. Evidence assumptions

- Evidence assigns an asset state `Compromised` or `Safe`. Unknown means no
  evidence.
- Evidence is treated as **certain and exact** (probability 1) for the
  stated node state. The framework does not model uncertain or partial
  evidence.
- **Impossible evidence** (a state with exactly zero probability under the
  model, e.g. a node with `p_base_override: 0` asserted as Compromised) is
  detected **before** inference and returned as a structured
  `IMPOSSIBLE_EVIDENCE` diagnostic with the affected nodes. It is never
  silently displayed as an all-zero result.
- Because probabilities are soft-capped to `[1e-6, 0.9995]`, exact zero can
  only arise from `p_base_override: 0`; the feasibility check flags evidence
  on such nodes. A residual edge case exists for structural zeros (a node
  with leak 0 and a parent with causal weight 1, where
  `P(child=0 | parent=1) = 0`): contradictory evidence on such a pair is not
  currently pre-checked and would surface as very small (not exactly zero)
  posteriors. This is documented in Section 12.

## 8. Risk-index assumptions

- `Risk Index = P(compromised | evidence) × Impact`, where
  `Impact = (severity/10) × scope_multiplier`, bounded in practice to
  `[0, 1.4]`.
- The risk index is a **bounded analytical/ranking measure**. It is **not**:
  - a probability (the product is not a probability),
  - an Annualised Loss Expectancy (ALE),
  - an expected monetary loss,
  - a universally standardised risk score.
- Risk levels (`Low/Moderate/High/Critical`) are defined by the **single,
  configurable** risk-threshold set (`risk_thresholds` in Settings, default
  0.25 / 0.50 / 0.75). The same thresholds drive the backend classification,
  the PDF report colours, and the frontend dashboard; nothing is hardcoded
  in the UI.

## 10. Calibration limitations

- **No parameter in this framework is empirically calibrated** from incident
  data in the delivered repository. Every numeric value is an expert judgment
  or a framework default.
- The framework provides two honest mitigations:
  1. Every parameter is **configurable** through Settings (validated
     server-side), so an organisation can substitute its own calibrated
     values.
  2. A **sensitivity analysis** capability (`backend/sensitivity.py`) lets an
     analyst quantify how much outputs (intrinsic probability, posterior,
     risk index, network-level risk) move when key assumptions (`k`, `x0`,
     propagation weights, exposure/patch multipliers) change.
- Changing model assumptions changes model outputs. The sensitivity module
  makes this dependence explicit; it does **not** produce confidence
  intervals, because no statistical uncertainty model is claimed.

## 11. Sensitivity limitations

- Sensitivity analysis perturbs one parameter at a time around its current
  value and records the response of each output metric. It does not:
  - explore the full joint parameter space,
  - model parameter correlation,
  - quantify sampling or measurement uncertainty,
  - provide statistical significance statements.
- It answers the question "how much would this output move if this assumption
  changed by X?" — nothing more.

## 12. Known limitations

1. No empirical calibration (see Section 10).
2. No live NVD/vulnerability retrieval; data is analyst-supplied.
3. Exact inference may not scale to very large/high-treewidth networks;
   measured guidance is in `tests/test_performance.py`.
4. Binary node states only; no continuous or multi-state assets.
5. Evidence is certain; no uncertain/partial evidence support.
6. Leak equals intrinsic probability; common-cause residual risk is not
   separately parameterised.
7. Risk index is a ranking measure, not expected loss.
8. Reports (CSV/PDF) use the same thresholds and definitions as the API; they
   inherit the same assumptions and limitations.
9. The firewall multiplier is a static per-link factor; defence-in-depth
   interactions are not modelled.
10. All defaults are framework defaults; organisations must calibrate.
11. Structural-zero evidence (a child with leak 0 and a parent with causal
    weight 1, evidenced in contradiction) is not pre-checked; it would
    surface as near-zero rather than exactly-zero posteriors. Only evidence
    on nodes whose own base probability is exactly 0 (`p_base_override: 0`)
    is detected as `IMPOSSIBLE_EVIDENCE` before inference.
